[Hermes Agent](https://github.com/nousresearch/hermes-agent) is an open-source agent from Nous Research. This example runs its [web dashboard](https://hermes-agent.nousresearch.com/docs/user-guide/features/web-dashboard), including the embedded terminal and coding tools, inside a Cloudflare container.

Each signed-in user gets a separate container. A Worker verifies Cloudflare Access authentication, forwards dashboard HTTP and WebSocket requests, and routes model calls through AI Gateway. The model credential stays outside the container.

## Prerequisites

- Node.js 22 or later and Docker running locally.
- A Cloudflare account with [Containers](/containers/) enabled.
- An [AI Gateway](/ai-gateway/get-started/) with [Unified Billing](/ai-gateway/features/unified-billing/) configured for `openai/gpt-4.1-mini`.
- A [Cloudflare Zero Trust organization](/cloudflare-one/setup/) for Access authentication.

## 1. Get the example

```sh
git clone https://github.com/irvinebroque/nous-research-hermes-agent-cloudflare-sandbox.git
cd nous-research-hermes-agent-cloudflare-sandbox
npm ci
npx wrangler login
```

The example uses the [native Container API](/containers/api/durable-object-container/) to manage lifecycle, proxy ports, and intercept outbound traffic. It does not require changes to Hermes or an additional Sandbox SDK dependency.

The Dockerfile pins a Hermes commit, builds the web frontend and Node terminal bundle, and installs Python dependencies from Hermes's lockfile. The startup script configures the `custom` model provider and `terminal` and `file` toolsets, then runs:

```sh
hermes dashboard --host 0.0.0.0 --port 9119 --no-open --skip-build
```

## 2. Configure Access and AI Gateway

Choose your Worker name in `wrangler.jsonc`. Your dashboard URL will be `https://<worker-name>.<workers-subdomain>.workers.dev`.

Create a [self-hosted Access application](/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/) for that complete hostname. Configure the [Google identity provider](/cloudflare-one/integrations/identity-providers/google/), select only Google for this application, and enable automatic redirect to the identity provider. If you need personal Gmail accounts and accounts from multiple organizations, configure an **External** Google OAuth audience.

Create an **Allow** policy for your intended users. Add each allowed email domain as a separate **Include → Emails ending in** entry. Include entries use OR logic, so the Google-authenticated address needs to match only one domain.

Enable [managed OAuth](/cloudflare-one/access-controls/applications/http-apps/managed-oauth/) for the Access application. For CLI OAuth clients, enable dynamic client registration and localhost/loopback redirect support. Managed OAuth adds an OAuth authorization-code flow for non-browser clients; Google authenticates browser users through Access.

Set these variables in `wrangler.jsonc`:

```json
{
  "vars": {
    "AI_GATEWAY_ID": "YOUR-GATEWAY-ID",
    "MODEL": "openai/gpt-4.1-mini",
    "ACCESS_TEAM_DOMAIN": "YOUR-TEAM.cloudflareaccess.com",
    "ACCESS_AUD": "YOUR-ACCESS-APPLICATION-AUD"
  }
}
```

The audience tag is available in the Access application's settings. These values are identifiers, not API keys. The AI binding authenticates model calls, so you do not need an inference token in a Worker secret or in the container.

:::note
Every user admitted by your Access policy can use your model and container budget. Choose the allowed email domains for your intended audience and configure AI Gateway rate limits for your deployment.
:::

## 3. Deploy and open the dashboard

```sh
npm run deploy
```

Open the Worker URL and sign in with Google through Access. The first request starts your container, which can take a minute. Open **Chat** and enter:

```text
Create hello.py and a unittest for it in /workspace.
Run the test and explain what you changed.
```

Approve tool requests in the dashboard when prompted. Hermes runs the task with its file and terminal tools. The dashboard's settings, sessions and workspace all belong to your container. Check AI Gateway to see the model requests.

You do not need to sign in to Hermes separately. The Worker obtains a private backend session from Hermes after Access has authenticated the request. The dashboard's sign-out action redirects to Access logout.

:::caution[Temporary workspace]
The example stops containers after 15 minutes of inactivity. Files, sessions, memory and settings are lost when a container stops or is replaced. Refreshing the page reuses a running container; an open WebSocket can keep it active. Export your work before leaving. For durable state, add [workspace save and restore](/sandbox/files/save-and-restore-a-workspace/) and preserve `HERMES_HOME` as well as your project files.
:::

## How authentication and isolation work

The Worker verifies the Access JWT's signature, issuer, audience and expiry. It derives the Durable Object ID from the verified identity, so two users cannot select the same container by changing a URL or request header.

Each Durable Object starts one container, waits for the dashboard's HTTP readiness, and forwards requests to port 9119 using `container.getTcpPort(9119).fetch(request)`. This supports the dashboard's WebSocket terminal as well as HTTP APIs and assets.

Hermes requires authentication when bound to `0.0.0.0`. The Durable Object generates a random backend password and logs in over the private container port. It replaces external credentials with this private session when forwarding requests and removes backend `Set-Cookie` headers from responses. Hermes's authentication stays enabled; the example does not use `--insecure`.

Managed OAuth clients use the same boundary. The application publishes discovery metadata at:

```text
https://<worker-name>.<workers-subdomain>.workers.dev/.well-known/oauth-authorization-server
```

OAuth clients must use PKCE and include the dashboard origin in their `resource` parameter. Access validates their bearer token and forwards a signed assertion for the Worker to verify.

## How model requests reach AI Gateway

Hermes's custom provider sends OpenAI-compatible requests to `https://model.internal/v1`. This is an intercepted hostname, not a public inference server. The container has Internet access disabled, and its outbound HTTPS handler allows:

- `POST https://model.internal/v1/chat/completions` for the configured model.
- HTTPS `GET` and `POST` to `github.com` for public repository access.

Other destinations are rejected. The handler limits model request size, validates the model name, and calls the AI binding:

```ts
const response = await env.AI.run(model, inputs, {
  gateway: { id: env.AI_GATEWAY_ID, skipCache: true },
  returnRawResponse: true,
});
```

Returning the raw response preserves model errors, streamed output and tool calls. The placeholder `OPENAI_API_KEY=provided-by-worker` satisfies Hermes's client configuration; it is not an API credential. Python and Git trust the container interception CA through `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE` and `GIT_SSL_CAINFO`.

The example uses GPT-4.1 mini. Hermes sends a default `reasoning_effort` option that this model rejects, so the outbound handler removes that field for this model. If you change models, choose one that supports Chat Completions and function calling, and check its supported options.

## Scope of the example

The dashboard and tools can control the entire per-user container. The network allowlist does not enable runtime package installation, arbitrary websites, private GitHub access, other model providers or Hermes's external integrations. This example demonstrates the native dashboard and coding tools; it does not host every Hermes feature.

The repository includes unit tests for authentication and forwarding, plus an offline Docker smoke test that drives the real dashboard's WebSocket terminal through a file-write and shell-tool round trip. Use the sample task above to verify live inference after deployment.
